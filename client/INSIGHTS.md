## Tool & Library Notes
- 2026-07-17 — **The i18n namespace IS the message filename, verbatim** — `client/src/i18n/request.ts:19-24` loads `messages/en/*.json` and keys each by `file.replace(/\.json$/, "")`, so a file's basename must EXACTLY equal the string passed to `useTranslations(ns)`. The repo convention is camelCase basenames (`agentPerformance.json`, `prReview.json`); a kebab-case name silently breaks. Hit with the Project Context feature: the catalog shipped as `context-attach.json` (namespace `context-attach`) while `ContextAttachTab.tsx:39` calls `useTranslations("contextAttach")` → `MISSING_MESSAGE: Could not resolve 'contextAttach'` at runtime. **Fix:** renamed the file to `contextAttach.json`. **Why it hides:** `ContextAttachTab.test.tsx` passed the catalog into `NextIntlClientProvider` as `messages={{ contextAttach: messages }}` — hardcoding the correct namespace by hand, bypassing the filename→namespace derivation the real app relies on — so the unit test was green while every page render threw. **Rule:** a component test that constructs the messages object literally does NOT prove the catalog is wired; the filename is the real contract. Match the JSON basename to the `useTranslations` string exactly, in camelCase.
- 2026-07-17 — Calling a SECOND `useTranslations("<other-namespace>")` inside an existing tab-shell component (to label one new tab pulled from a shared namespace) does NOT fail loudly — `next-intl` logs `IntlError: MISSING_MESSAGE` to stderr and returns a fallback string, it does not throw, so every pre-existing test for that component keeps passing (green) while quietly spamming stderr on every run. Hit adding a `context` tab to `SkillEditor.tsx`: its tab labels resolve via `t(tb.labelKey)` under the `skills` namespace, and a second `useTranslations("contextAttach")` for just that one label made ALL of `SkillEditorPane.test.tsx`'s 6 (unrelated, unowned) tests log the missing-message error every render, even though `vitest run` still reported them passing. Confirmed by literally running the file before/after. **Fix used:** render a literal string (`"Context"`) for that one tab's label instead of adding the namespace lookup, since the component's existing tests only ever supply `{ skills: messages }` to `NextIntlClientProvider` and are out of this task's ownership to update. **Rule:** before adding a `useTranslations(ns)` call to a component with existing tests, check what messages object those tests pass to `NextIntlClientProvider` — a component that renders correctly in prod (which loads every namespace) can still be quietly polluting every consuming test's stderr, and `pnpm exec vitest run` alone won't surface it as a failure.
- 2026-07-16 — **`@testing-library/user-event` is NOT a dependency** of `client/` — don't reach for `userEvent.setup()`, the import fails at collection with "Failed to resolve import". Every interactive test here uses `fireEvent` from `@testing-library/react` (precedents: `ConventionsView.test.tsx`, `FindingsPanel.test.tsx`, `SeverityFilter.test.tsx`, `RunTraceDrawer.test.tsx`). For a controlled `Textarea`/`TextInput`, `fireEvent.change(el, { target: { value: "…" } })` is the way. Also note `getByDisplayValue` is unreliable for a multi-line textarea body — grab it with `container.querySelector("textarea")` instead.

## Recurring Errors & Fixes
- 2026-08-08 — `pnpm exec vitest run "<path>" "<path2>"` treats each positional arg as a SUBSTRING filter against test file paths, not a literal path — a path missing one real segment (e.g. omitting `OverviewTab/_components/` between `_components/` and `PrBriefCard/`) doesn't error, it silently matches zero files: `No test files found, exiting with code 1`. Hit running a plan-provided Verify command `.../_components/PrBriefCard` for test files that actually live at `.../_components/OverviewTab/_components/PrBriefCard/PrBriefCard.test.tsx` (missing the `OverviewTab/_components` segment). The corrected/full path ran the same tests green. When a Verify command reports zero tests found, check the path is a real substring of the actual test file path before assuming red — it may be a copy/paste path typo in the plan, not a code defect.
- 2026-06-25 — `formatCost` trailing-zero bug: using `usd < 0.01 ? 4 : usd < 1 ? 3 : 2` gives 3 decimal places for `0.06` → `"$0.060"`. Fix: `usd.toFixed(4).replace(/(\.\d{2}.*?)0+$/, '$1')` — formats to 4 dp then strips trailing zeros while keeping minimum 2 decimal places. See `client/src/components/run-cost-badge/RunCostBadge.tsx:9`.
- 2026-06-29 — Dismissed findings inconsistency in `ReviewRunAccordion`: `bySeverity` severity counts must filter `!f.dismissed_at` just like the `blockers` count on the line above does — otherwise pills show a higher number than blockers, contradicting each other. Pattern: any time you count `review.findings` by severity in the client, always prepend `.filter((f) => !f.dismissed_at)`. Fixed at `client/src/app/repos/[repoId]/pulls/[number]/_components/ReviewRunAccordion/ReviewRunAccordion.tsx:58-63`.
- 2026-07-04 — The vendored icon registry (`client/src/vendor/ui/icons.tsx:64,147`) exports lucide's `Pencil` icon only under the key `"Edit"` (`Edit: Pencil` alias) — `IconName` has no `"Pencil"` key. Passing `icon="Pencil"` to `Button`/`EmptyState`/etc. fails typecheck ("not assignable" against the full `IconName` union). Use `icon="Edit"` for a pencil/edit glyph. Hit in `client/src/app/skills/_components/SkillsListView/SkillsListView.tsx` (Edit button in the skill preview panel).
- 2026-07-17 — **A give-up deadline written as a `Date.now() > deadline` check INSIDE the effect that watches for the success signal never fires on the exact path it exists to guard.** `ResyncButton` polls `/index-state` until `lastIndexedSha` moves off the sha it started from; the timeout branch originally lived in that same `useEffect`, deps `[startedFrom, currentSha, deadline, prId, qc]`. When a resync degrades (`no_clone`/`sync_failed` — the server still returns 202 and the sha **never** changes), no dep ever changes, so React never re-runs the effect, so the deadline is never evaluated and the button spins forever. The polling query re-fetching every 1.5s does NOT rescue it: TanStack Query hands back an identical `lastIndexedSha` string, so the dep is `Object.is`-equal and the effect stays dormant. **Fix:** a real `setTimeout` in its own effect keyed on the in-flight flag, with `clearTimeout` cleanup disarming it when the signal arrives or the component unmounts — see `client/src/app/repos/[repoId]/pulls/[number]/_components/OverviewTab/_components/BlastCard/ResyncButton.tsx`. **Rule:** anything whose trigger is the ABSENCE of a change must be driven by a timer, never by an effect body — an effect runs only when something changed, which is precisely what is not happening on the failure path. **Why it hides:** it works in every manual test, because a human clicking around always causes some re-render. Only a test that advances fake timers with no re-render in between catches it (`ResyncButton.test.tsx` "gives up instead of spinning forever") — a test that clicks twice masks it, since the second click re-runs the handler.
- 2026-07-17 — **A tab-editor's `?tab=` allowlist must be DERIVED from its tab list, never hardcoded alongside it — a separate literal drifts the moment a tab is added.** `AgentEditorView.tsx` hardcoded `const VALID_TABS = ["config", "skills"]` while the tab bar rendered from `AgentEditor/constants.ts` `TABS` (which already included `context`). `tab` is recomputed each render as `VALID_TABS.includes(search.get("tab") ?? "") ? … : "config"`, so clicking **Context** wrote `?tab=context` and the very next render snapped it back to `config` — the tab was unreachable. **Fix:** export `VALID_TABS = TABS.map((t) => t.key)` from `AgentEditor/constants.ts` and import it, exactly as `SkillEditor/constants.ts:26` + `SkillEditorPane.tsx:29` already do (that editor was correct precisely because it derives). **Rule:** when a component both renders tabs from a list AND validates `?tab=` against an allowlist, the allowlist must be `TABS.map(t => t.key)` — two independent sources of truth for the same tab set is the bug.
- 2026-07-08 — A `styles.ts` map typed `Record<string, CSSProperties>` CANNOT hold a function member (e.g. a dynamic `confFill(pct) => ({...})`) — and if you drop the `Record<...CSSProperties>` annotation to allow the function, every static object literal then widens (`flexDirection: string`, `overflowX: string`, `resize: string`) and fails assignment to `style`. Fix: keep the static map typed `Record<string, CSSProperties>` and export dynamic styles as **standalone functions** with an explicit `: CSSProperties` return. See `client/src/app/conventions/_components/ConventionsView/_components/ConventionCard/styles.ts` (`confFill` exported separately from `cs`).

## Recurring Errors & Fixes
- 2026-07-16 — RTL testing a "stat strip" (the `BlastTab`/`BlastCard` pattern: `<span style={s.stat}><span className="tnum">{count}</span>{label}</span>` repeated per metric) — `screen.getByText("1")` throws "multiple elements found" whenever two stats share a value (e.g. `symbols: 1, endpoints: 1`), since each numeric `<span>` is its own exact-text DOM node. Assert on the stat LABEL text (`"symbols"`, `"callers"`) instead of the bare numeric value, or scope with `within()` on the specific `<span style={s.stat}>` container. Hit writing `BlastCard.test.tsx`.
- 2026-07-16 — **An "honest degradation" badge is dead code if an earlier early-return can render the empty state first.** Both `BlastTab.tsx:45-53` and `BlastCard.tsx:64-75` computed `degradationSentence(...)` AFTER their `if (data.changed_symbols.length === 0) return <EmptyState .../>` branch — so the one case where the explanation matters most (index degraded AND nothing indexed) rendered a bare "No blast radius data" with no badge and no reason, which is exactly what the requirement forbids. Every test passed: they only covered degraded-WITH-data and empty-WITH-healthy-index, never the intersection. **Fix pattern:** compute the degradation/explanation state ABOVE every early return and render it INSIDE each branch (`BlastCard.tsx` now builds a `banner` const before the empty check and an `emptyExplanation(index_state)` that folds the degradation reason in — render exactly one of them, not both stacked, or the sentence prints twice). **Why it hides:** an empty-state early-return reads as the "nothing to show" path, so it doesn't feel like a place that owes the user an explanation — but "we have nothing" is precisely when they need one. When a feature has a "never show an empty screen" rule, write the test for `degraded && empty` specifically; the two single-axis tests will both pass while the corner is broken.
- 2026-07-16 — `vi.mock("@/lib/hooks/blast", () => ({ useBlast: () => mockResult }))` (a static object-literal factory, no `importOriginal`) is a COMPLETE module replacement — any export the mocked module gains later that the component starts calling unconditionally (a second hook, e.g. `useExplainBlast` added to `blast.ts` for the T4 "explain" mutation) is `undefined` inside the mock and throws at render (`TypeError`/"No export is defined on the mock") even though the real module exports it fine. **Why:** vitest module mocks don't merge with the real module unless the factory explicitly spreads `await importOriginal()`. A prior task's test file (T3's `BlastCard.test.tsx`) that predates a later task's new hook call (T4) will break the moment the later task lands, purely from this. Fix: add a stub for the new export to the existing mock's return object (`useExplainBlast: () => ({ mutate: vi.fn(), isPending: false, isError: false, data: undefined })`) — no assertion changes needed, just complete the mock's shape. When authoring a NEW hook-mock from scratch, prefer the `importOriginal`-spread form specifically to avoid this class of breakage for whoever adds the next hook to the same module.
