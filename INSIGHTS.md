- 2026-07-17 — **`./scripts/e2e.sh` is hermetic in its PORTS only, not in Next's build dir — running it while `./scripts/dev.sh` is up corrupts the running dev server.** It isolates Postgres/API/web onto alt ports (`:5440`/`:3101`/`:3100`) but starts the web with `(cd client && pnpm exec next dev -p "$WEB_PORT")` (`scripts/e2e.sh:148`) from the SAME `client/` dir, and `client/next.config.*` declares no `distDir` — so both dev servers read and write one `client/.next`. The e2e run rewrites `.next` underneath the running server and its teardown kills the compile mid-flight; the live server then throws `Cannot find module '…/.next/server/middleware-manifest.json'` (MODULE_NOT_FOUND) on every request, which looks like a broken build but is not. **Fix when hit:** stop the dev stack, `rm -rf client/.next`, restart — the cache is disposable and no source or git state is involved. **Avoid:** don't run e2e alongside a dev server, or give e2e its own `next dev --dist-dir`. Two more traps in the same script: `e2e/` deps are NOT installed by `dev.sh` (root CLAUDE.md: `cd e2e && npm install`), and `agent-browser` is an **undeclared global CLI dep** — it is in no `package.json`, so when it is absent the whole stack still boots green and every flow fails with `spawn agent-browser ENOENT`.

- 2026-07-17 — **Claude Code's agent-frontmatter parser is MORE LENIENT than strict YAML — do not "fix" an agent file because PyYAML/js-yaml rejects it.** `.claude/agents/implementation-planner.md:3` holds `description: … Read-only: it never edits code and never authors a specification; …`. That embedded `: ` (colon-space) inside a plain scalar makes strict YAML throw `mapping values are not allowed here`, so a validation script like `yaml.safe_load(src.split('---\n')[1])` reports the agent as broken. **It is not broken:** the pattern predates the rename (present at `HEAD:planner.md`) and the agent loads fine — it was announced as an available agent type mid-session with that exact description intact. So strict YAML is the wrong gate for agent validity; it produces false alarms that tempt you into rewriting a working description. Validate an agent by whether Claude Code lists it, not by a third-party parser. (Corollary hit in the same session: `git show HEAD:x > /tmp/f` then reading `/tmp/f` from **Windows Python** fails with `FileNotFoundError` — git-bash's `/tmp` is not Python's; same root cause as `INSIGHTS.md:33`. Use a real Windows path or the scratchpad when handing files between git-bash and a native tool.)
## Decisions
- 2026-07-17 — **Confining ONE subagent's writes requires a `hooks:` block in that agent's OWN frontmatter; `permissions.deny` in `settings.json` cannot express it, and a `PreToolUse(Write|Edit)` gate is decorative unless you ALSO withhold `Bash`.** Built for `spec-creator`, which may only write specification markdown (`.claude/agents/spec-creator.md` frontmatter → `.claude/hooks/spec-creator-write-scope.sh`, 21/21 allow/deny cases verified incl. Windows backslash paths, `..` traversal, and its own agent file). **Why not `permissions.deny`:** deny rules are session-wide and subagents inherit them *unconditionally* — a subagent cannot override or add exceptions (`permissionMode` in frontmatter is even ignored outright under parent auto/bypass modes) — so `Edit(...)`-style deny rules would have gagged `implementer`/`test-writer`/`doc-writer` too. Frontmatter hooks are the only per-agent lever: they run ONLY while that agent is active and are torn down when it finishes. **Why no `Bash`:** the hook matches tool names, so an agent holding `Bash` walks around a `Write|Edit` gate with `echo > file` — the barrier is only real if the tool list has no other write path (`tools: Read, Grep, Glob, Edit, Write, Skill`; the cost is the agent cannot shell out for e.g. `date`, so the caller must supply it). Two more facts worth knowing: `PreToolUse` payload carries `agent_id`/`agent_type` **only** when the call originates in a subagent (usable as a defence-in-depth check if a hook ever moves to `settings.json`), and `Write(...)` is NOT a valid deny-rule prefix — file writes are covered by `Edit(...)`. Sources: https://code.claude.com/docs/en/sub-agents, https://code.claude.com/docs/en/hooks, https://code.claude.com/docs/en/permissions.
- 2026-07-16 — `devdigest-mcp/` deliberately does NOT vendor `@devdigest/shared`, even though every other consumer (`server/`, `client/`) does. **Why:** the MCP package only speaks HTTP+JSON to the Fastify API (never imports server `src/`), so the handful of fields it needs (`Repo.full_name`, `PrMeta.id|number`, `Agent.id|name`, `Finding.severity|title|file|start_line`, `ConventionCandidate.rule|evidence_path|confidence|status`) are cheaper to redeclare as narrow local types/Zod schemas in `devdigest-mcp/src/{types,schemas,resolve}.ts` than to maintain a third hand-synced vendor copy (dual-vendor sync cost per `INSIGHTS.md:21` above, now tripled). The trade-off accepted: local shapes can silently drift from the real DTO if the server changes a field name — mitigated only by hermetic tests asserting the exact trimmed shape (`devdigest-mcp/test/trim.test.ts`). See `docs/plans/2026-07-16-devdigest-mcp-server.md` "Constraints" + "Planning notes".

- 2026-06-25 — Both `server/src/vendor/shared/` and `client/src/vendor/shared/` must receive **identical** Zod contract changes in the same commit. Missing one side causes runtime Zod parse failures that are hard to trace. There is no automated sync — it is manual by convention.
- 2026-07-16 — (extends the 2026-07-15 "grep vendor contracts first" note below to **pre-seeded i18n messages**) `client/messages/en/*.json` files also ship ahead of the feature, and their keys encode the DESIGN'S intended scope — so **a plan that tells implementers to ignore existing message keys is a plan disagreeing with the design.** `client/messages/en/blast.json` shipped `view.{tree,graph}` and `graph.{empty,ariaLabel}`; `docs/plans/2026-07-16-blast-radius.md` declared Graph mode out of scope and instructed "ignore `view.graph` and `graph.*`" and "do not let their presence tempt a Graph implementation". The approved mockup had a Tree/Graph toggle all along — the keys were the standing signal and the plan explicitly overrode it, so T2/T3 shipped a card+tab split with no graph and had to be redone (T9–T11). **Rule:** before finalising scope, grep `client/messages/en/<feature>.json` and treat every unused key as a scope question to resolve against the design, not noise to suppress. If you still decide to cut it, say WHY the key exists and is not being used — "ignore it" is what made this cost a rewrite.
- 2026-07-15 — When planning a feature that "needs a new contract," **grep `*/src/vendor/shared/contracts/` first** — later-lesson contracts often already ship pre-vendored as stubs. Smart Diff's `SmartDiff`/`ProposedSplit` shapes already existed byte-identically in both `server/src/vendor/shared/contracts/brief.ts` and the client copy (verified with `diff`), so the planned "add contract + dual-vendor sync" task was unnecessary and the contract became a read-only dependency — which is what let the backend and frontend tasks run **fully parallel** with zero shared-file ownership. Complements the dual-vendor sync rule above: check whether the sync is even needed before scheduling it.
- 2026-07-17 — The dual-vendor-sync rule (line 26 above) assumes both copies of a contract file already agree; that assumption can be FALSE for a type simply unused by the client. `AgentVersionConfig`/`AgentVersion` (`contracts/knowledge.ts`) existed ONLY in `server/src/vendor/shared/` — the client copy had never received it at all (zero client-side consumers: `grep -r AgentVersion client/src` → no hits), even though every other type in that file was already synced. A plan that says "extend `AgentVersionConfig` in both copies" can therefore silently assume a base that isn't there in one of them. **Before extending any existing shared type across both vendor copies, `diff` the two contract files first** (not just re-read the one you expect to edit) — if the type is one-sided, the "extension" is really an add-the-whole-type-then-extend, and you must reconstruct the missing copy to be byte-identical to the (about-to-be-extended) source before applying the shared change, or the two copies stay divergent by more than your diff.
- 2026-07-17 — (synthesises 26/27/28/29 above and adds the engine-seam layer) **A DevDigest feature's groundwork ships pre-seeded across THREE independent layers — Zod contracts (`*/src/vendor/shared/contracts/`), i18n namespaces (`client/messages/en/*.json`), and the reviewer-core engine seam (`reviewer-core/src/prompt.ts` inputs/renderers) — and each can independently be present-or-absent. The presence of one implies NOTHING about the others.** The Project Context feature proved all three states at once: the engine seam was fully built and wired shut (`specs` input + `## Project context` renderer + `assembly.specs`, `prompt.ts:116-119,139,158`), the i18n namespace (`context.json`) shipped ahead **with a wrong empty-state body and deliberately-unconsumed editing keys**, while the DTOs (`ContextDoc`/`ContextAttachment`) were genuinely absent (and `AgentVersionConfig` was even one-sided — entry 29). **Rule when scoping any lesson-feature: grep all three layers separately before writing the plan** — `contracts/` for the shape, `messages/en/<feature>.json` for the design's intended UI scope (every unused key is a scope question, not noise — entry 27), and the engine (`reviewer-core`/run-executor seam) for an input that already exists and must NOT be rebuilt (reviewer-core is shared with the CI runner; modifying it breaks it). Assuming "new feature ⇒ all-new plumbing" schedules work that's already done in one layer and misses a wrong-but-shipped asset in another.
- 2026-07-17 — (extends entry 30 with TWO more pre-seeded layers and a shape-mismatch twist, from the Why+Risk Brief feature — `specs/2026-07-17-why-risk-brief.md`) **The pre-seeded groundwork is not only the three CODE layers of entry 30 — it also reaches a DB TABLE and a FEATURE-MODEL REGISTRY SLOT, and a pre-seeded contract can be shaped for a DIFFERENT concern than the one you're about to build.** The Brief feature turned out "almost free" because five things already shipped: the cache table `pr_brief {pr_id PK, json jsonb}` (`server/src/db/schema/reviews.ts:57-62` — so NO new table/migration), the `risk_brief` `FeatureModelId` model-resolution seam (`contracts/platform.ts:17,60` + `settings/feature-models.ts:51` — so the model is resolved via `resolveFeatureModel`, never hardcoded), and the `Risk`/`RiskSeverity` contracts (`contracts/brief.ts:47,50-57`). **The trap:** the pre-seeded `PrBrief {intent,blast,risks,history}` (`contracts/brief.ts:116-122`) looked like the feature's output contract but was shaped as the *input bundle* (a composition of the L03/L04 building blocks), NOT the requested LLM output `Brief {what,why,risk_level,risks[],review_focus[]}`. Repurposing it would have broken the input shape; the right move was a NEW sibling contract (`Brief`/`ReviewFocus`/`BriefEnvelope` added additively, both vendor copies byte-identical). **Rule when scoping a lesson-feature: grep FIVE seams, not three — `contracts/` (and check whether a same-named contract is shaped for input vs output before extending it), `messages/en/<feature>.json`, the reviewer-core/run-executor engine seam, AND `db/schema/*` for an existing table + `settings/feature-models.ts` for an existing model slot.** A pre-seeded contract whose NAME matches your feature but whose SHAPE serves a different concern is entry 27's "unused key is a scope question" one level up: the whole type is the scope question — add alongside, don't overload.

## Recurring Errors & Fixes
- 2026-07-16 — On Windows, `git mv <dir> <dir>` fails with `fatal: renaming '…' failed: Permission denied` **while the Next dev server is running** — Windows refuses to rename a directory that any process holds a handle on, and the dev-server watcher holds recently-compiled route folders. **The files inside are NOT locked, only the directory**: `mkdir -p` the destination and `git mv` each file individually, and it succeeds (git still records them as renames, so history follows). Hit while moving `client/src/app/skills/[id]/_components/SkillEditor`; its sibling `SkillEditorView` moved fine in the same command, so a *partial* failure is expected here and does not mean the tree is corrupt — re-check with `git status` before retrying. Don't kill the user's dev server for this, and don't fall back to `cp`+`rm` (loses rename detection).
- 2026-07-16 — In a **fresh `git worktree`, `cd server && pnpm typecheck` fails with errors that look like broken product code but are just missing deps in a SIBLING package.** `git worktree add` checks out tracked files only, so each package's gitignored `node_modules/` is absent. Because `reviewer-core` is consumed as TypeScript **SOURCE** via a tsconfig path alias (root CLAUDE.md), tsc type-checks its files as part of the server program — so the server typecheck reports `TS2307: Cannot find module 'openai'` / `'zod'` at `../reviewer-core/src/llm/*.ts` and a couple of `TS2322 'unknown' is not assignable to 'T'` in the adapters. **Fix:** install per package before believing any typecheck (`cd reviewer-core && npm install`, `cd client && pnpm install` — reviewer-core uses npm, the others pnpm). After that the same command is clean. Don't chase these as a regression from your own change.
- 2026-06-25 — `.claude/settings.local.json` was accidentally committed with Windows-specific absolute paths. Added to `.gitignore` and removed with `git rm --cached`. If you see this file reappear after a merge, it is not ignored upstream — re-run `git rm --cached .claude/settings.local.json`.
- 2026-07-16 — In `devdigest-mcp`, every `server.registerTool(...)` handler that returns `toToolResult(err)` (`devdigest-mcp/src/errors.ts:20`, `ToolErrorResult`) from its catch block fails `tsc` with "Index signature for type 'string' is missing in type 'ToolErrorResult'" — the MCP SDK's `CallToolResult` (`@modelcontextprotocol/sdk/types.js`) is inferred from a loose Zod object (`z.core.$loose`) so TS requires a matching implicit index signature, which a plain named interface like `ToolErrorResult` doesn't have; a freshly-created object literal would be exempt, but the value returned from a function call is not "fresh" so the exemption doesn't apply. **Fix (used in every tool handler's catch block):** `import type { CallToolResult } from '@modelcontextprotocol/sdk/types.js'` and `return toToolResult(err) as CallToolResult;` — see `devdigest-mcp/src/tools/list-agents.ts:56`, `devdigest-mcp/src/tools/get-conventions.ts:72`. Every later tool file (`run-agent-on-pr.ts`, `get-findings.ts`, `get-blast-radius.ts`) needs the same cast.
- 2026-07-15 — Constructing a `RegExp` from a JS **string** (`new RegExp('^\\s*-\\s*'+x+'\\s*$','m')`) inside a `node -e "..."` argument that itself sits inside a Bash-tool `<<'EOF'`/double-quoted command silently strips every backslash (`\s` -> `s`), so the check always fails even though the target file is correct. **Why:** multiple escaping layers (Bash-tool command string -> git-bash double-quote unescaping -> JS string literal parsing) each consume one level of `\\`, and it's easy to under/over-escape without noticing since the script still runs (no syntax error, just a wrong pattern). Fix: write verification scripts as a real `.js` file via a **quoted heredoc** (`cat > file.js <<'EOF' … EOF`, `node file.js`) and prefer plain string ops (`line.trim() === '- ' + name`) over dynamically-built regexes with `\s`/`\\` for anything driven through nested Bash escaping — confirm with a regex **literal** (`/^\s*-\s*x\s*$/m`) first if you need to sanity-check the target content is fine before suspecting the file.
- 2026-07-16 — In `devdigest-mcp`, calling `guardCharacterLimit(payload)` (`devdigest-mcp/src/trim.ts:57`, generic constraint `T extends Record<string, unknown>`) with a variable that holds the return value of a named helper function (e.g. `guardCharacterLimit(trimBlastRadius(dto))` where `trimBlastRadius` returns a plain `interface TrimmedX`) fails `tsc` with the same "Index signature for type 'string' is missing" error as the `ToolErrorResult`/`CallToolResult` case above (`INSIGHTS.md:28`) — a named interface without an index signature isn't assignable to `Record<string, unknown>`, and the "fresh object literal" exemption only applies to a literal written directly at the call site, not a value flowing through a function return. **Fix:** spread the helper's result into a fresh literal at the call site — `guardCharacterLimit({ ...trimBlastRadius(dto) })` — instead of casting or adding an index signature to the interface (`devdigest-mcp/src/tools/get-blast-radius.ts:120`). Same root cause as the `CallToolResult` entry (loose-Zod-inferred type wants an implicit index signature TS only grants to fresh literals), different call site and a different (spread, not `as`) fix — worth knowing both shapes exist before reaching for `as` reflexively.
- 2026-07-17 — (complements the 2026-06-25 `.claude/settings.local.json` note above, which covers it being committed in the first place) **`git checkout <branch>` silently OVERWRITES a gitignored file when that path is tracked on the target branch** — you get no "would be overwritten by checkout" error, because that guard only protects files that are untracked AND unignored. `.claude/settings.local.json` is in `.gitignore:3` but is still **tracked on the older lesson branches** (`main` only untracked it at `430e227`), so `git checkout 4-MCP` replaced the user's live file with the branch's blob, and the follow-up `git rebase origin/main` then **deleted** it outright (main doesn't track it) — taking their permission allowlist with it. The user is never warned and the file is invisible in `git status` afterwards. **Recover from the blob, not from memory:** `git ls-tree <branch> -- .claude/settings.local.json` → `git show <blob-sha> > .claude/settings.local.json`. **Why this repo specifically:** the no-workspace layout means several long-lived branches (`1-claude_md`, `2-SKILLS`, `3-AGENTS`, `4-MCP`) disagree about whether this path is tracked, so ANY checkout between them can clobber local settings. Before switching branches, run that `ls-tree`; if it prints a blob, back the file up first.
- 2026-07-17 — **Rebasing a lesson branch onto `main` after the PREVIOUS lesson branch was rebased-and-merged produces conflicts that are pure duplicate history, not real disagreements — never hand-merge them.** The course branches stack (`2-SKILLS` → `3-AGENTS` → `4-MCP`), so branch N carries branch N-1's PRE-rebase commits; once N-1 lands on `main` with rewritten hashes, `git rebase origin/main` drops most of them as "skipped previously applied commit" via patch-id — but any commit whose patch shifted during N-1's own rebase (context lines, an auto-merged `INSIGHTS.md`) has a **different patch-id** and conflicts instead. The conflict markers then show main's fuller version (which already contains your change *plus* later ones) against the older incoming one, so resolving by hand re-introduces stale code. **Instead: prove the content is already upstream, then `git rebase --skip`** — `git diff origin/main <backup-branch> -- <module paths>` printing nothing means byte-identical. Measured: `3-AGENTS` 56 commits → 7 (all duplicates auto-dropped, zero conflicts); `4-MCP` 11 → 4, where `2fad407` (intent) needed an explicit `--skip` and git then auto-dropped `27c6d1e` (smart-diff) on its own once the tree matched. **Always branch a backup first** (`git branch backup/<name>-prerebase <name>`) — it is what makes the "is this really a duplicate?" diff possible, and the only way back if a `--skip` was wrong. Also beware a stale local `main`: `git fetch` before judging, or `git merge-base --is-ancestor main <branch>` will cheerfully report a branch is already up to date when `origin/main` has moved on.
