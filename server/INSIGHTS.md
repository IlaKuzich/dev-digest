## What Doesn't Work
- 2026-08-26 — A structural-string security lint over a GitHub Actions `workflow.yml` that only inspects the FIRST `permissions:` occurrence (e.g. `lines.findIndex(l => l.trim().startsWith("permissions:"))`) is a full escalation bypass — GitHub Actions allows a `permissions:` block at BOTH the workflow level and per-job (`jobs.<job-id>.permissions`), and a job-level block REPLACES the workflow-level one for that job, it is NOT merged. An attacker can keep a fully-compliant top-level block (passing a naive "first block only" check) while granting broad scopes in a job-level override that actually governs the job. Caught by `pr-self-review` against `server/src/modules/ci/generators/lint.ts`'s AC-48 re-lint — fixed by finding and validating EVERY `permissions:` line in the file regardless of nesting/indent (`lines.map(...).filter(...)` collecting all indexes, then checking each block independently), not just the first. Any future lint over multi-block YAML keys (permissions, env, etc.) must assume the key can legally repeat at different nesting levels and check them all.
- 2026-08-25 — A structural-string security lint that does a plain `contents.includes("pull_request_target")` check will FALSE-POSITIVE on `generators/workflow.ts`'s own generated output — its header comment literally reads `# ⚠️  Do not add write: to permissions or use pull_request_target.` (`generators/workflow.ts:27`), so the forbidden term appears in a comment before any real trigger section. The AC-48 re-lint (`generators/lint.ts:checkNoPullRequestTarget`) must filter out comment-only lines (`l.trim().startsWith("#")`) before substring-scanning, or it hard-rejects the very output it's meant to allow. Any future structural (non-YAML-parsing) lint added to this generator must line-filter comments the same way before substring/keyword checks — verified by a direct unit test asserting `lintWorkflowYml(workflowYml(...)) === {ok:true}` (`server/src/modules/ci/service.test.ts`).
- 2026-07-08 — `server/test/indexer-pipeline.test.ts` fails 6/11 on Windows with `ENOENT` at its own `writeFileAt` helper (`test/indexer-pipeline.test.ts:144`) — the tmp-dir file write, before the indexer runs. It is an OS/tmp-path flake in the test setup, NOT a product regression (source `src/modules/repo-intel/pipeline/*` untouched). Don't chase it as a break from an unrelated change; the rest of the server unit suite is green.
- 2026-07-16 — (corrects the 2026-07-08 note above) The `ENOENT` in `indexer-pipeline.test.ts`'s `writeFileAt` (`test/indexer-pipeline.test.ts:140-145`) is NOT a random OS/tmp-path flake on Windows — it is a deterministic bug in the helper. `join(root, rel)` normalises the WHOLE joined path to backslashes on win32 (even though `rel` like `'src/util.ts'` is written with forward slashes), so the helper's own `full.lastIndexOf('/')` then returns `-1`, the `if (slash > 0)` guard skips `mkdir` entirely, and the subsequent `writeFile` fails because the parent dir was never created. It reproduces 100% of the time on Windows, not intermittently. **Why:** manual `/`-splitting after `path.join` is unsafe cross-platform — use `path.dirname(full)` instead (verified fix in `server/test/depgraph.test.ts`'s own `writeFileAt`, which has none of these failures). Not fixed in `indexer-pipeline.test.ts` itself here (out of scope for T7) — a future task touching that file should apply the same one-line fix.

## Tool & Library Notes
- 2026-07-16 — `import.meta.resolve('some-pkg')` (used to get an absolute path to a dependency without loading it) throws `__vite_ssr_import_meta__.resolve is not a function` under Vitest's SSR/vite-node transform (`server/src/adapters/depgraph/index.ts`, T7) — Vite's `import.meta` stub doesn't implement `.resolve`, even though the identical call works fine under plain `node`/`tsx`. Also ruled out: `createRequire(import.meta.url).resolve('dependency-cruiser')` fails with `ERR_PACKAGE_PATH_NOT_EXPORTED` for any ESM-only package whose `package.json#exports` has no `"require"`/`"default"` condition (dependency-cruiser 17.x only exports `"import"`) — CJS `require.resolve` cannot see it at all. **Working alternative** when a child process needs a package that only the PARENT process's cwd can resolve as a bare specifier: spawn the child inheriting the parent's cwd (not the target dir), let the child's own `await import('pkg')` resolve normally first, THEN have the child `process.chdir()` to the target dir before doing the cwd-sensitive work — see `RUNNER_SCRIPT` in `server/src/adapters/depgraph/index.ts`. This needs zero path resolution in the parent and works identically under `tsx`, `vitest`, and a `tsc`-built `dist/`.
- 2026-07-17 — `vi.spyOn(fsPromisesNamespace, 'readFile')` (importing `* as fsPromises from 'node:fs/promises'` then spying on the namespace object) throws `TypeError: Cannot redefine property: readFile` under Vitest 2.1 — the node built-in's ESM export bindings aren't configurable, so `Object.defineProperty` (what `spyOn` uses under the hood) fails. **Working alternative:** `vi.mock('node:fs/promises', async (importOriginal) => { const actual = await importOriginal(); return { ...actual, readFile: vi.fn(actual.readFile) }; })` at the top of the test file (vitest hoists `vi.mock` regardless of literal position) — this replaces the module in vitest's OWN module registry rather than mutating the live namespace object, so every consumer that imports `readFile` from `'node:fs/promises'` (including the module under test) resolves to the wrapped mock, while every other export (`mkdtemp`/`writeFile`/`unlink`/etc.) passes through to the real implementation via the spread. Remember to `vi.mocked(readFile).mockClear()` between assertions if multiple tests/calls share the one mock instance (it isn't per-test). Used to assert "no bytes were read" for an oversized-file crash guard in `server/test/context.it.test.ts` (T3, `docs/plans/2026-07-17-project-context.md`).

- 2026-07-17 — `TiktokenTokenizer.count` (`adapters/tokenizer/index.ts`, real `js-tiktoken` `cl100k_base` BPE, not the `approxTokens` fallback) is **catastrophically slow on a long run of a single repeated character** — encoding `'x'.repeat(70_000)` pegged a test-runner process at 100% CPU for 500+ seconds (measured: `Get-Process` showed 568s of accumulated CPU time and it was still climbing when killed) versus sub-second for equivalent-length realistic prose. This is the classic BPE-merge worst case (a long run of one byte creates a huge number of valid merge candidates every pass) — not specific to js-tiktoken, but easy to hit BY ACCIDENT in a test fixture (`'x'.repeat(N)`, `'a'.repeat(N)`, etc. are exactly this shape). **Two implications:** (1) any hermetic/it test that needs a "big text" fixture for a token-estimate assertion MUST override `ContainerOverrides.tokenizer` with a cheap counter (`{ count: approxTokens }`) rather than pass a huge repeated-character string through the REAL tokenizer — see `server/test/context.it.test.ts` and `server/test/context-injection.it.test.ts` (T4, `docs/plans/2026-07-17-project-context.md`). (2) **latent production risk**: T4's AC-18 pre-flight overflow check (`reviews/run-executor.ts`) calls `this.container.tokenizer.count(...)` unconditionally on every review run's attached project-context text + the whole assembled prompt, and that text comes from a repo clone any PR author can influence (server/INSIGHTS.md's own untrusted-input framing for this feature) — an attached `.md` doc containing a long run of a repeated character (still well under the 5 MB `CONTEXT_MAX_DOC_BYTES` crash guard, so it isn't rejected) could pin a worker process on CPU for minutes per review. Not fixed here (out of T4's scope — the pre-flight check is required to use the existing `Tokenizer` port per the spec's own module-boundary note); flagging for whoever next touches `TiktokenTokenizer` or the AC-18 overflow path to decide whether to cap input length before encoding or swap in a streaming/chunked encode.
- 2026-08-26 — `drizzle-kit generate`'s auto-derived FK constraint name (`<table>_<column>_<ref_table>_<ref_column>_fk`) can exceed Postgres's 63-byte identifier limit on a table with a long name referencing another long-named table — e.g. `multi_agent_run_agents_multi_agent_run_id_multi_agent_runs_id_fk` (67 chars) in migration `0020_high_lilandra.sql`. Postgres silently truncates it (a `NOTICE`, not an error — `code: '42622'`), so the migration still applies cleanly; only watch for it if a SECOND FK on the same table would truncate to an IDENTICAL prefix, which would then collide as a duplicate constraint name. Not an issue here (only one long FK on this table) — flagging so a future table with 2+ long FK pairs checks the generated SQL's constraint names, not just table/column/index names, per the existing "read the generated SQL" rule (2026-07-04 above).
- 2026-07-17 — (fixes the "not fixed here" note directly above — architecture-review W1) Direct benchmark of `js-tiktoken`'s `cl100k_base.encode()` on `'x'.repeat(n)` (isolated script, not through the app): 1,000 chars ≈ 126 ms, 2,000 ≈ 452 ms, 4,000 ≈ 1.6 s, 8,000 ≈ 6.7 s — worse than quadratic, confirming the scaling that produced the 500+s hang at 70,000 chars. Fixed in `reviews/run-executor.ts`'s AC-18 check by (a) moving BOTH `Tokenizer.count` calls inside the `MODEL_CONTEXT_WINDOWS[agent.model] !== undefined` gate, so an unmapped model does ZERO encode work (previously only the size *comparison* was gated, not the encode itself — the actual CPU cost), and (b) routing every count through a new `estimateTokensBounded(tokenizer, text)` (`context/helpers.ts`) that caps the REAL encoder to the first `TOKENIZER_SAFE_CHAR_LIMIT = 2_000` characters (`context/constants.ts`) and falls back to the O(n) `approxTokens` heuristic for any remainder — this bounds the COUNTING cost only, never truncates what's actually sent to the model. Test coverage (`context-injection.it.test.ts`'s AC-18 case) spies on the count fn to assert every call's argument length ≤ 2,000 for a mapped model, and zero calls at all for an unmapped one.

## Open Questions
- 2026-07-16 — The repo-intel write pipeline is **non-transactional with the status stamp last**: `deleteAllForRepo`/`deleteForFiles` → `insertSymbols` → `insertReferences` → `replaceEdges` → `resolveReferences` → `replaceFileRank` → `replaceFileFacts` → `upsertIndexState` are 8+ separate DB calls (`pipeline/full.ts:204-281`, `incremental.ts:205-275`). A crash/OOM/JobRunner timeout anywhere before the final `upsertIndexState` leaves the PREVIOUS run's `repo_index_state` row (`status:'full'` + old counts) describing tables the interrupted run already wiped or half-rewrote — and `getBlastRadius`'s persistent path trusts that row. Compounding it: `withTimeout` (`platform/resilience.ts:13-24`) is a bare `Promise.race` that never cancels the underlying handler, and there is no per-repo lock anywhere in `platform/jobs.ts` / `repo-intel/service.ts`, so a timed-out run keeps mutating rows while a second user-triggered resync starts concurrently against the same `repoId`. Not reproduced (would need a forced >120s run raced with a second trigger) but every supporting piece is citable. **Open:** does this warrant a transaction around the write block, an advisory lock per `repoId`, or stamping `status:'indexing'` first? Also note `defaultIsRetryable` (`resilience.ts:35-65`) does NOT match `TimeoutError` (no `.status`/`.code`), so `full.ts:14`'s docstring claim of "rejects → failed+retry" is wrong today — no retry happens.
- 2026-07-16 — `extractCrons` (`adapters/codeindex/extract.ts`) only matches in-code scheduling calls (`cron.schedule(...)`, `CronJob(...)`, `register`/`enqueue('kind')`). A **Vercel Cron Job declared in `vercel.json`'s `crons` array** — which triggers an App Router route with no in-code scheduling call at all — is structurally invisible: `.json` isn't even in `SUPPORTED_EXT` (`repo-intel/constants.ts:14`), so the file is never walked. This is the same blind spot T8 just fixed for `extractEndpoints` (Express/Fastify-only patterns → zero endpoints on every Next.js repo), one heuristic over. On the persistent path `crons_affected: []` is presented as fact ("0 crons"), so for a Vercel-cron repo that zero would be a confident lie rather than an honest none. Verified the sample repo has no cron patterns at all (`grep -rl "cron\|schedule\|CronJob\|enqueue" src` → nothing), so its `[]` is currently honest — the gap is latent, not active. **Open:** widen `extractCrons` + `SUPPORTED_EXT` to read `vercel.json`, or keep crons on the "unknown" affordance until a detector can actually see them?

## Decisions
- 2026-07-28 — Promoting an agent version forward-only (`modules/eval/service.ts:promote`) must call `agentsRepo.setSkills(agentId, config.skills...)` BEFORE calling `AgentsService.update()`, not after. `AgentsRepository.update` snapshots the NEW `agent_versions` row by reading `skillIdsForAgent(row.id)` synchronously inside the same call (`agents/repository.ts:172`) — whatever the link table holds AT THAT MOMENT becomes the new version's `skills` snapshot. Re-linking after `update()` returns produces a new version whose recorded skills don't match the promoted version's. A module reusing `AgentsService.update()` to re-apply a historical `AgentVersionConfig` must always sequence any skill-link mutation before the update call, not after.
- 2026-07-16 — **The `// parity with agent versioning` comment in `server/src/modules/skills/repository.ts` was false, in the one way that matters.** Agents snapshot the **NEW** config under the **NEW** version (`agents/repository.ts:151`, plus v1 at insert `:111`), so the newest `agent_versions` row always equals the live agent. Skills snapshotted the **PRIOR** body under the **OLD** version — so the live version was **absent from its own history**, and a freshly created skill had **no rows at all**. Any read path built on `skill_versions` therefore rendered a history missing its own "current" entry. Fixed by aligning skills to the agent write path (insert → snapshot v1; body edit → snapshot new body at new version); pre-existing rows stay compatible because v1..v_{n-1} hold identical content either way, and the missing live-version row is synthesized on read by `versionHistory()` in `skills/helpers.ts`. **Why:** rewriting history (rolling back) would break eval reproducibility — a past run must stay scored against the exact text it saw. Restore is therefore forward-only: `SkillsService.restoreVersion` re-applies an old body through the normal `update()` path, appending v_{n+1}. Note: agents have **no restore at all** — only list/get — so there is no precedent to copy for one.
- 2026-07-16 — `agents/repository.ts:155` `snapshotVersion` uses `.onConflictDoNothing()`; the skills snapshot originally did not. This is not cosmetic: `skill_versions` is PK'd on `(skill_id, version)`, so any write that lands on an existing pair (a restore, a retried save) throws a PK violation instead of no-oping. Keep `.onConflictDoNothing()` on every snapshot insert.
- 2026-06-25 — Use `NUMERIC(12,6)` not `double precision` for any financial column (cost_usd). `double precision` drifts for financial values; `NUMERIC` is exact. Drizzle's `numeric()` returns values as **strings** at runtime — add `Number()` casts in every read path (`run.costUsd != null ? Number(run.costUsd) : null`) and `String()` casts on write. See `server/src/db/schema/runs.ts:32`, `server/src/modules/reviews/repository/run.repo.ts`, and `server/src/modules/pulls/routes.ts`.
- 2026-07-16 — Fixed a cwd-sensitive library call (dependency-cruiser's tsconfig-`paths` resolution, `server/src/adapters/depgraph/index.ts`, T7) by running it in a dedicated child process rather than `process.chdir()` in the shared server process. Rejected `process.chdir()` in-process even wrapped in try/finally: the repo-intel indexer runs as a background job (`JobRunner`) that can be mid-await while OTHER async work (concurrent HTTP requests, other job handlers) runs on the same event loop, and `process.cwd()` is genuinely global — a `finally` restores it eventually, but any code that reads `process.cwd()` while the mutation is live sees the wrong value, and Node offers no per-async-context cwd. A short-lived child process (`node --input-type=module -e '<script>'`, exits immediately after) makes the `chdir` invisible to everything else, at the cost of one process-spawn (~tens of ms) per index run. Chosen over `baseDir`/inline-`tsConfig`-with-absolute-`baseUrl` because both were tested and neither affects dependency-cruiser's alias resolution at all — only `process.cwd()` does.

- 2026-07-15 — `_shared/schemas.ts:11` `IdParams` is hardcoded to the param key `id` (`z.object({ id: z.string().uuid() })`). - 2026-07-15 — A table keyed only by another entity's id (e.g. `pr_intent` PK'd on `pr_id`, `server/src/db/schema/reviews.ts:48`, no `workspace_id` column) is an IDOR trap: a repository method that filters by that id alone (`eq(t.prIntent.prId, prId)`) is NOT workspace-scoped even though the module "feels" tenant-scoped. Any read reachable from a route must join to the owning entity's table and filter on its `workspace_id` too (mirror `getPull`'s `and(eq(pullRequests.workspaceId, ...), eq(pullRequests.id, ...))`) — see the fix in `server/src/modules/intent/repository.ts` (`getIntent` now inner-joins `pull_requests`). When adding a new child table without its own `workspace_id`, check every repository method against this, not just the ones that "look like" writes.
- 2026-07-15 — For file-path pattern matching (glob-like `*.snap`, `**/index.ts`, `dist/**`) where the root `INSIGHTS.md:25` rule against dynamically-built `RegExp` applies, a small recursive segment matcher using only `split('/')`/`startsWith`/`endsWith`/`indexOf` works fine and needs no regex at all — see `matchPath`/`matchSegment` in `server/src/modules/smart-diff/classifier.ts:33`. Pattern precedence tables live in a sibling `constants.ts` so the matcher itself stays free of literals — reuse this pair (`constants.ts` patterns + `classifier.ts` matcher) for any future path-classification feature instead of reaching for `minimatch`/regex.
- 2026-07-15 — To integration-test the workspace-tenancy guard on a route whose service reuses `PullsService.getDetail` (e.g. `smart-diff/service.ts:27`), you do NOT need a second `AuthProvider`/context override — `LocalNoAuthProvider` always resolves the SAME default workspace regardless of which PR id is requested, so simply insert a second `t.workspaces` row + repo + PR under it and request that PR's id; `getById(workspaceId, prId)` (default ws, other PR) returns undefined → `NotFoundError` → 404 `not_found`. See `server/test/smart-diff.it.test.ts` ("rejects a PR belonging to another workspace").
- 2026-07-15 — Path-traversal guards that are purely lexical (`resolve`+`relative`, e.g. `safeRepoPath` in `server/src/modules/intent/helpers.ts:103`) do NOT stop a symlink planted inside the scanned root from pointing anywhere on disk — a committed symlink (or a symlinked parent dir) resolves lexically inside the root but its real target can be outside it. The fix pattern: keep the lexical check as a pure pre-filter in `helpers.ts`, then in the I/O layer (`service.ts`) `lstat` the candidate and reject if it's a symlink, AND `realpath` both the root and the candidate and re-check containment on the REAL paths (`isRealPathContained` in `helpers.ts:113`) — a symlinked ancestor directory escapes `lstat`-on-the-leaf alone, so both checks are needed. Re-derive any extension/allowlist check from the realpath'd target, not the lexical name.
- 2026-07-16 — `pull_requests` (`server/src/db/schema/pulls.ts:5-34`) has NO `merged_at` timestamp column — only `status` (enum incl. `'merged'`) and `updated_at`. Any DTO needing a `merged_at`-shaped field (e.g. `PriorPr` in `server/src/modules/blast/service.ts`, T11) must derive it as `status === 'merged' ? updatedAt?.toISOString() ?? null : null` rather than reading a dedicated column — this is a best-effort proxy (an import/resync could bump `updated_at` for reasons unrelated to the merge), not an exact merge timestamp. Don't add a migration for this alone; it's a read-time derivation.
- 2026-07-16 — **The repo-intel index is a snapshot of the repo's DEFAULT BRANCH, so files a PR ADDS are invisible to every index-backed feature** — they have no `symbols` rows, therefore no callers, endpoints or crons. This is not a bug and not a degraded index: new code genuinely has nothing depending on it yet. But it means a large PR can legitimately report a tiny blast radius on a healthy `status: 'full'` index, which reads to a user as "nothing is affected". Measured on `IlaKuzich/next_js_harness_testing#3`: 22 changed files / +1592 lines → only **3** `changed_symbols`, because only 2 of the changed files (`src/app/admin/layout.tsx`, `src/ui/components/header/header-user.tsx`) existed on `main`; the 18 new `src/api/orders/**` + `src/app/api/orders/**` files were absent from the clone entirely (verified: `ls server/clones/.../src/api/` → only `payments`, `reviews`). **Any feature reading the index against a PR's changed files must report its own coverage**, not just its results — see `toCoverage` in `server/src/modules/blast/helpers.ts` (`{changed_code_files, analyzed_files, unanalyzed_files}`), which the UI renders as "2 of 20 changed code files analyzed — the other 18 are new in this PR". Filter the denominator to `ANALYZABLE_EXT` (`blast/constants.ts`) first: a changed `bun.lock`/`package.json` is not a coverage gap, and counting it manufactures a caveat instead of reporting one. Distinct from the `index_state.degraded` badge — the index is healthy here, so reusing the warn-coloured degradation banner for this would cry wolf.

## Recurring Errors & Fixes
- 2026-08-08 — A Fastify route whose Zod `body` schema must accept a bodyless POST (e.g. `POST /pulls/:prId/brief` serving both a no-flag cached read and `{regenerate:true}`) needs `.nullish()`, NOT `.optional()`. Fastify's default JSON body parser yields `null` (not `undefined`) for a request sent with no payload/no Content-Type (verified via `app.inject({ method: 'POST', url })` with no `payload` key) — `fastify-type-provider-zod`'s validator then runs `schema.safeParse(null)`, and `ZodOptional` only accepts `undefined`, so `null` fails with a 422 `invalid_type` (`"expected":"object","received":"null"`). `BriefRequest.nullish()` (accepts `undefined` OR `null`) fixes it; `req.body?.regenerate ?? false` still reads correctly either way. See `server/src/modules/brief/routes.ts`.
- 2026-06-25 — When re-adding a column that a previous migration dropped (migration 0009 dropped `cost_usd`), create a new migration (0010, then 0011) rather than editing the original. The DB has already applied 0009; editing it would cause `pnpm db:migrate` to silently skip the edit.
- 2026-06-25 — **Manually created `.sql` migration files are invisible to `pnpm db:migrate` unless added to `server/src/db/migrations/meta/_journal.json`.** Drizzle's migrator reads the journal, not the filesystem. Only `pnpm db:generate` adds journal entries automatically. If you hand-write a `.sql` file, you must also append an entry to `_journal.json` with the correct `idx`, `tag` (filename without `.sql`), `version: "7"`, `breakpoints: true`, and a `when` timestamp. Missing this causes "column does not exist" 500 errors at runtime even after `pnpm db:migrate` succeeds.
- 2026-07-04 — Migrations `0010_add_cost_usd_agent_runs.sql` and `0011_change_cost_usd_to_numeric.sql` were hand-authored (per the note above) and never got a matching `meta/0010_snapshot.json` / `0011_snapshot.json`. Because `drizzle-kit generate` diffs against the LATEST snapshot file on disk (not the actual DB or a full re-scan), the next `pnpm db:generate` after those two (migration `0012`, `server/src/db/migrations/0012_wandering_runaways.sql:1`) diffed against the stale `0009_snapshot.json` and phantom-regenerated `ALTER TABLE "agent_runs" ADD COLUMN "cost_usd" numeric(12,6)` — a column that already exists — which would fail on any DB that already ran 0010/0011. Caught by manually inspecting the generated SQL before committing; fixed by deleting the stray statement (the new `0012_snapshot.json` drizzle-kit writes alongside it IS a full-state snapshot matching current `schema.ts`, so it repairs the chain going forward — confirmed by re-running `pnpm db:generate` afterward and getting "No schema changes, nothing to migrate"). **Lesson: after ANY `pnpm db:generate`, read the generated `.sql` before committing — a hand-authored migration anywhere in the history can make a later auto-generated one silently redundant/wrong.**
- 2026-07-17 — (corrects the 2026-07-16 "nothing re-indexes automatically" note above, which said "refresh/resync only from explicit user action" and thereby implied Refresh was one of the two working triggers) **The Refresh button could never advance the index at all — only resync could.** `RepoService.refresh` (`server/src/modules/repos/service.ts`) enqueued `REFRESH_JOB_KIND` alongside a `CLONE_JOB_KIND`, but `SimpleGitClient.clone()` (`server/src/adapters/git/simple-git.ts:57-61`) short-circuits on an already-cloned repo to a bare `simpleGit(dest).fetch()` — which moves `origin/<branch>` and leaves local HEAD **and the worktree** on the old sha. `runIncremental` then reads `currentHead()` (a bare local `git revparse HEAD`, `:90-92` — it never fetches), sees `currentHead === lastIndexedSha`, and no-ops. Forever. Only `sync()` (`:77-88`) does `fetch` + `reset --hard origin/<branch>`, and it is reachable ONLY from `RESYNC_JOB_KIND` (`repo-intel/routes.ts`, `POST /repos/:id/resync`) — which had no UI button, so the only reachable path was the broken one. Measured on `IlaKuzich/next_js_harness_testing`: index pinned at `133 files / a0f6cb2` across repeated Refreshes even after PR #3 merged to `main`; a single `POST /resync` → `153 files / dec36f1` immediately. **Fixed** by having `refresh()` enqueue `RESYNC_JOB_KIND` instead — `resyncRepo` does its own `sync()` so it advances regardless of the clone job's queue position and needs no cross-kind ordering guarantee (p-queue doesn't FIFO across kinds); the clone job stays enqueued because `resyncRepo` degrades to `no_clone` when there is no clone yet and the clone's own INDEX follow-up covers that path. **Why it hid:** the symptom is silence. A stale index reports `status:'full'` with honest-looking counts, Refresh returns `200 {status:'refreshing'}`, and `repo_index_state.updated_at` even advances (via `touchIndexState` on the `sha_unchanged` branch) — only `lastIndexedSha` betrays it. When verifying any reindex trigger, assert on `lastIndexedSha`/`filesIndexed`, never on the endpoint's response or `updated_at`. `RepoService.refresh` had **zero tests**, which is how this shipped; `server/test/repos-refresh.test.ts` now asserts which kinds get enqueued and was verified to fail against the old code.
- 2026-07-28 — **`fastify-type-provider-zod` types `req.body` from the Zod schema's INPUT type, so a `z.unknown()` (or otherwise-optional-input) field reads as OPTIONAL on `req.body` even after validation** — passing `req.body` straight into a service whose input interface declares that field REQUIRED is a `TS2345` ("`X` is optional … but required in type"). Hit on `POST /agents/:id/eval-cases` where the body's `expected_output: z.unknown()` (from the shared `EvalCaseInput` contract) is required by `EvalService.createCase`. Fix: normalize at the route boundary — `expected_output: req.body.expected_output ?? []` before the service call (`server/src/modules/eval/routes.ts`). Note a `.default([])` on the schema does NOT fix this: `.default()` only changes the OUTPUT (`z.infer`) type, not the INPUT type Fastify infers `req.body` from. **Why:** the type-provider deliberately types the handler's `req.body` as the pre-parse input shape.
- 2026-07-28 — **`pnpm exec vitest run <file>` transpiles via esbuild and does NOT type-check, so a task whose `Verify` is vitest-only passes green while `pnpm typecheck` still fails.** Two classes slipped past task-local Verify this way and only surfaced at the plan's end-to-end gate: (1) `noUncheckedIndexedAccess` violations on bare array indexing inside a tight loop — `adjacency[i]`/`matchOfProduced[j]` in the augmenting-path match at `server/src/modules/eval/scoring.ts` (fix: hoist to a local `const x = arr[i]!` with a one-line in-range justification, or a bounds guard); (2) the Fastify/Zod input-optionality `TS2345` above. **Lesson:** when a task adds indexed-access-heavy pure code OR a route↔service type boundary, include `pnpm typecheck` in that task's own verification — do not rely on `vitest run <file>` alone to prove it type-safe. `server/tsconfig.json` has `noUncheckedIndexedAccess` enabled, so this is a standing trap for any array-index-heavy module.
