## Where the run departed from the design

- **A spawned implementer was resumed by a channel outside the orchestrator for ~2 days after its task finished, and the design has no mechanism to prevent, detect, or bound this.** Agent #4's assigned task was "Implement T1 server data model" — schema, migration, one shared contract. Its own completion report (captured earlier in this session) put that work at **127,223 subagent tokens**. `collect.mjs` shows its *lifetime* total at **65.0M tokens across 222 turns and 1439 minutes** — a >500x blowup, entirely from resumes I never sent (the roster's `Resumes` column reads `—` for #4: the orchestrator warm-resumed it zero times). Concretely, this is why the git working tree kept showing content I hadn't written: a `client/src/app/repos/[repoId]/multi-agent/page.tsx` + `MultiAgentLandingView` that appeared fully-formed before I'd built it, a `nav.ts` href that reverted itself between two different designs across turns, and — per the overlap table below — direct writes into T2/T3/T4's *and my own* file territory, none of it in the plan's `Owns` lists for T1.
  - **Concurrent writes, #4 against files it was never assigned:** `server/src/modules/reviews/{routes.ts, repository.ts, multi-agent.service.ts, repository/multi-run.repo.ts}`, `server/test/multi-agent.it.test.ts` (all T2's `Owns`), `client/src/vendor/ui/nav.ts`, `client/src/lib/hooks/multi-agent-results.ts`, `client/src/app/repos/[repoId]/multi-agent/[number]/_components/MultiAgentResultsView/{MultiAgentResultsView.tsx, styles.ts}`, `client/messages/en/multiAgent.json` (T4's `Owns`, and later files I was editing directly myself).
  - This is not a plan-design failure — the plan's own `Owns` lists were genuinely disjoint across T1–T4 (confirmed by plan-verifier Mode A and Mode B, both clean). It is a **channel-authorization failure**: nothing stops a human from resuming a named subagent directly, and the resumed agent has no way to know its new instructions didn't come from the orchestrator that scoped its task.
  - **How it was caught:** not by any gate in the chain — by the orchestrator treating every "done" claim as unverified and independently re-running `git status`/tests/typecheck after each reported completion, and by reading the plan file fresh instead of trusting a "reverted" claim. That practice is exactly what prevented a real defect from shipping; it was improvised mid-run, not something the design asked for.
- **Cold-spawned a second architecture-reviewer (#10) instead of resuming the first (#8) for a small follow-on review.** #8 already held full context on the feature's architecture; #10 paid a fresh cold start (3.0M tokens, $2.65) to re-derive it for one incremental diff. This is exactly the anti-pattern the README's "reuse a warm agent via SendMessage" rule warns against, and unlike the point above, this one is on me — a plain execution miss, not a channel problem.
- **Everything the orchestrator itself controlled held to design:** Mode A ran before any implementer; the plan's ≤2-concurrent-implementer cap was honored (T2‖T3, not a wider wave); the architecture-review fix loop was one bounded pass, all fixes applied inline (small, contained — correctly not routed to a subagent per the "do small work inline" rule) and re-verified by the same finder (#8), not a fresh spawn; Mode B traced all 31 ACs to PASS with 0 MISSING/PARTIAL; pr-self-review ran and recorded a clean 0-blocker verdict. Model choice was correct throughout (opus for spec/plan reasoning, sonnet for recognition-axis review/verification/implementation), and sonnet's architecture-review findings were real and correctly scoped, not shallow — no evidence the sonnet downgrade is costing quality on this task shape.

## Where the design itself was wrong

1. **The chain assumes single-writer control of every spawned agent, and nothing enforces or even flags a violation.** `.claude/agents/README.md`'s entire fix-loop and file-ownership model rests on "the orchestrator is the only one issuing `SendMessage`s" — but any tool that lets a human address a named/pinned agent directly (as happened here) can resume it with instructions the orchestrator never sees, and the agent has no way to distinguish that from a legitimate resume. The blast radius this run: one agent's cost went from a rounding error to the second-most-expensive line item in the whole session, and its unscoped writes could easily have silently clobbered a sibling task's file if timing had gone differently — the append-only luck that saved `client/INSIGHTS.md` in the 2026-07-28 retro was not available here, since these were full-file rewrites, not appends. There is no proposed fix in the existing README for this; it is a genuinely new failure mode, not a recurrence of the `INSIGHTS.md` ownership gap from the prior two retros.
2. **The design has no "verify before trusting" step baked in for subagent self-reports — it worked here only because the orchestrator added one unprompted.** Every phase in `implement`'s runbook trusts a subagent's "done" report as the input to the next phase. This run needed an extra, informal layer — re-running each task's own `Verify` command independently, `git status`-checking scope after every completion, re-reading a plan file instead of trusting a "reverted" claim — that caught the channel-authorization problem above. That layer worked, but it isn't written down anywhere, so the next orchestrator (a fresh session, no memory of this retro) has no reason to add it.

## Worth changing before the next run (ranked, each tied to a number above)

1. **Document "verify, don't trust" as a standing step in the `implement` runbook, not an improvisation.** After every implementer/reviewer "done" report, re-run its own `Verify` command and `git status`/`git diff --stat` the claimed file list before marking the task complete. This run's entire defense against the channel-authorization problem was exactly this, done ad hoc — codifying it means the next orchestrator does it by default instead of by luck. Highest priority: it is the one practice that actually contained the biggest risk in this run.
2. **Resume the finder for incremental follow-on reviews instead of cold-spawning.** Would have saved #10's $2.65 + cold-start context re-derivation; small in isolation, but a clean, avoidable instance of a rule already written down.
3. **No concrete fix is proposed for the channel-authorization gap itself** (item 1 under "design was wrong") — it may not be fixable from inside `.claude/agents/README.md` at all, since it's a property of what tools can address a named agent, not of the orchestration rules. Flagging it for the user to decide whether it's addressable (e.g., a naming/handoff convention when a subagent is meant to be driven interactively) rather than proposing a rule change I'm not confident fixes it.

**Note on the money (partially refutes the doctrine, this run):** the README's rule of thumb — "the biggest sink is rarely the code; it's cold restarts and verbose reports" — holds for #2 (implementation-planner, $77.24, the single biggest line item, inflated by 2 resumes, one of which was pure damage-control undoing the unauthorized test-writer restructuring) but is beaten entirely by a **third category the doctrine doesn't name**: uncoordinated externally-driven agent activity. #4's $32.59 *understates* its impact — its cost-per-token (~$0.50/M vs. ~$1.50–2.50/M for every other sonnet agent) is suspiciously low for 65.0M tokens, almost certainly because a long, many-times-resumed lifetime is dominated by cheap cache-read reuse across turns rather than fresh generation — meaning the dollar figure hides the real cost, which was the orchestrator's own time spent discovering, reconciling, and re-verifying work it never asked for. That reconciliation overhead is folded into the orchestrator's own $122.99 (the single largest bucket in the whole run) and isn't separately visible in this table at all.
